# SaveMoney: устройство проекта

## Идея

SaveMoney помогает планировать личный бюджет по методу конвертов. Пользователь
учитывает доходы и обязательные платежи, задаёт лимиты категорий, записывает расходы
и откладывает деньги на цели. Главные показатели — доступная сумма, дневной лимит
и остатки конвертов.

Конечный продукт включает мобильное приложение на React Native и десктопное
приложение на Tauri с React и TypeScript. Оба клиента будут работать с общим
Python API. На текущем этапе реализовано ядро с демонстрацией в терминале;
контракт будущего сервера описан в [README.md](README.md#api-будущего-restful-сервера).

## Архитектура

Ядро разделено на модели, расчёты и сценарии работы с бюджетом:

- `savemoney/domain/models.py` — доходы, обязательства, категории, периоды,
  конверты, операции, цели и настройки; проверка допустимых значений.
- `savemoney/domain/money.py` и `dates.py` — денежный ввод и календарные правила.
- `savemoney/domain/calculations.py` — вычисление баланса, резервов, лимитов и накоплений.
- `savemoney/domain/validation.py` — проверка хронологии накоплений.
- `savemoney/budget.py` — связи между объектами, операции и закрытие периодов.
- `savemoney/http_client.py` — отдельный учебный клиент requests.
- `main.py` — воспроизводимая демонстрация бюджета.

Данные хранятся в словарях в памяти. После завершения процесса они исчезают.
Ядро не зависит от HTTP и базы данных. На последующих этапах транспорт и постоянное
хранилище подключаются вокруг этих правил.

## Деньги и даты

Все суммы задаются целыми копейками. `float` не используется для финансовых
расчётов: например, 45,50 ₽ хранится как 4550. Ввод с дробной копейкой отклоняется.
Максимальная сумма ограничена безопасным целым JavaScript, чтобы будущие клиенты
не теряли точность при чтении JSON.

Внутри ядра используются календарные даты `datetime.date`. В API даты представлены
строками `YYYY-MM-DD`. Если выплата назначена на 31-е число короткого месяца,
используется последний день этого месяца. Нерегулярные доходы не дают прогнозной
даты следующей выплаты.

## Баланс и дневной лимит

Баланс текущего календарного месяца складывается из доходов и изъятий из целей
за вычетом расходов и пополнений целей. Будущие и удалённые операции не учитываются
в фактическом балансе на выбранную дату.

Из баланса вычитается резерв неоплаченных обязательств до ближайшей выплаты.
При отсутствии прогнозируемого дохода горизонт расчёта — конец месяца.
Получается сумма, доступная для повседневных расходов. Она может быть отрицательной.

Дневной лимит — доступная сумма, делённая на число дней до горизонта расчёта
с округлением вниз до копейки. При нулевом количестве дней возвращается вся сумма.
Это месячная модель бюджета; перенос остатка конверта сам по себе не создаёт доход.

## Конверты и закрытие месяца

Категории имеют не больше двух уровней. Расход в подкатегории уменьшает остаток
и её конверта, и конверта родительской категории. Остаток равен плановому лимиту
плюс перенесённая сумма минус расходы.

При появлении нового месяца создаются его конверты с прежними плановыми лимитами.
Завершившийся месяц ожидает разбора остатков. Для каждого конверта выбирается:

- `burn` — закрыть без переноса;
- `carry_over` — перенести остаток в конверт следующего месяца;
- `to_goal` — перевести положительный остаток в выбранную цель.

Повтор одинакового решения не создаёт повторного перевода. Другое решение для уже
закрытого конверта отклоняется. После первого решения операции разбираемого месяца
нельзя менять: иначе зафиксированный остаток перестанет соответствовать истории.
Пустой завершённый месяц закрывается автоматически.

Для пересекающихся конвертов родителя и ребёнка денежное решение допускается
только у одного из них; второй закрывается через `burn`. Это предотвращает
повторное распределение одних и тех же денег.

## Цели и удаление операций

Накопления вычисляются из пополнений и изъятий. Добавление или удаление операции
не должно создавать отрицательные накопления ни в один из дней истории.
Операции внутри одного дня учитываются суммарно: точное время текущая модель
не хранит. Операции удаляются мягко и перестают участвовать в расчётах.
Перевод, созданный при закрытии конверта, нельзя удалить отдельно от решения.

## Проверки

Общая команда — `sh scripts/check.sh`: Ruff, проверка форматирования, pytest,
покрытие строк приложения 100% и компиляция Python-модулей.
Полный набор включает проверки согласованности README и OpenAPI.
Покрытие строк Python-приложения — 100%.
Использованы Python 3.13.1, coverage 7.17.2 и Ruff 0.17.3.

Четыре HTTP-теста используют временный сервер на локальном порту для проверки
requests. Это тестовая фикстура. Сервер приложения и его маршруты ещё не реализованы.
Результат удалённого CI проверяется отдельно в GitHub Actions.

## Документация API

Контракт сохранён в `openapi.json` в формате OpenAPI 3.0.3. Он описывает все
38 операций из README, типы и ограничения полей, обязательные связи, статусы
и примеры. `swagger/index.html` использует Swagger UI 5.34.1; версия ресурсов CDN
зафиксирована и проверяется браузером по SHA-384. Страница не отправляет запросы
к API, пока сервер не реализован.

Публичная документация: https://tru3ty.github.io/SaveMoney_app/.
Ветка `gh-pages` содержит только страницу, OpenAPI JSON и `.nojekyll`.
При обновлении контракта в неё копируются `swagger/index.html` как `index.html`
и корневой `openapi.json`. Основные ветки не сливаются ради публикации документации.

Для локального просмотра можно собрать временный каталог:

```sh
preview_dir=$(mktemp -d)
cp swagger/index.html openapi.json "$preview_dir/"
python -m http.server 8081 --directory "$preview_dir" --bind 127.0.0.1
```

Открыть `http://127.0.0.1:8081/`. Это просмотр статических файлов, а не сервер приложения.
Для загрузки Swagger UI нужен доступ к CDN `unpkg.com`.
